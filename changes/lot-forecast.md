### Added

- `dialecte lot forecast [<id>] [--json] [--against <lot>]`: the conflict forecast of a lot's work, against main and against every other open lot of its store, without a checkout. A lot's work is its worktree's HEAD plus its uncommitted work, taken as one snapshot commit on a copy of the worktree's index (`add -A`, `write-tree`, `commit-tree` with a fixed identity and date, so the same work gives the same sha); the worktree's index, refs and files are never written, and ignored files stay out. Main is `origin/<base>` as last fetched, never fetched by the forecast. Each comparison is one `git merge-tree --write-tree`: `clean`, `conflict` (each path with its kind, `content` with the line ranges between the conflict markers, `modify/delete` and the others without lines), `exclusive` (every conflicted path is a lock file: `package-lock.json`, `npm-shrinkwrap.json`, `pnpm-lock.yaml`, `yarn.lock`, `bun.lock`, `bun.lockb`) or `unknown` with its reason (git older than 2.38, a damaged lot, `worktree of <lot> missing`, `<ref> does not resolve`, `snapshot of <lot> failed: ...`, `merge-tree failed: ...`, `forecast of <lot> over 20 s`: each git step is limited to 20 seconds, and a step over it is killed). Each comparison also lists the files both sides changed (`shares`), even when the merge is clean. A path that conflicts against main for either lot is reported once, on the main line, never on the pair line. The lot's verdict is the worst of its comparisons: unknown > conflict > exclusive > clean. Default lot: the one whose worktree holds the current folder; `--against <lot>` compares with main and that lot only. Exit 0 clean, 1 conflict or exclusive, 3 unknown, 2 usage or refusal (a damaged lot, a lot no longer open - committed, canceled or failed - or a simulated one: `lot forecast: <lot> is <state>: only an open lot has a forecast`, `--against` the lot itself or a lot of another store); every exit but 2 prints on standard output. A clean forecast does not promise a semantic merge (a renamed function another lot calls), three lots landing together, or work not written yet.
- The lot folder's `forecast.jsonl`: one line per comparison, the lines of a run written in one append, sharing its `run` id and its count `of` (`{ schema: 1, run, at, trigger, of, self, main, against, other?, verdict, shared?, conflicts?, more?, moreShared?, reason? }`); each line within 4,096 bytes: at most 10 shared paths, 10 conflict paths and 3 ranges per path, the paths left out counted in `moreShared` and `more`. A reader takes the newest complete run; a torn last line, a line that does not read and the lines of a run with fewer lines than its `of` are counted, never read. Each run also writes a `forecast` event to the lot's events (`run`, `trigger`, `verdict`, the count per verdict, `durationMs`). Nothing reads the record yet: `lot start`, `lot scope`, `lot land`, the gate, the card, `lot status` and `plan next` are wired in a later release.
