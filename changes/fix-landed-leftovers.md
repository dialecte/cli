### Fixed

- `lot close` and `worktree prune` ask two questions instead of one before removing a worktree or a branch: is the lot's current work landed (a merged lot's branch holding commits beyond its landed tip and its cut keeps it: `<n> commit(s) made since its landing: <commits>`), and would this removal lose a commit (`<n> commit(s) its removal would lose: <commits>`). A worktree removal takes its HEAD and HEAD reflog, a branch deletion its tip and reflog; a commit only they reach is lost unless a surviving branch tip or branch reflog, a tag, a landed tip or a remote-tracking ref (not origin's copy of the deleted branch) holds it, or holds a byte-equal patch of it (`git patch-id --verbatim`; a merge, a root or an empty commit is held by ancestry only). So a lot whose heads two rebases replaced closes, and a commit made on a detached HEAD keeps the worktree even after the branch is checked out again.
- `lot close` closes a worktree whose branch was reset or rebased away from some of its commits: the branch reflog still holds them, and the closed line names them with git's reflog expiry (`gc.reflogExpireUnreachable`); deleting that branch would lose them, so `worktree prune` keeps it.
- `lot close` checks what a removal would lose even when no base branch resolves (it closed with no check before).
- `lot close` and `lot land` ask the host for every lot they read, pushed by `lot land` or not: a pull request opened by hand, its branch deleted on origin after a squash merge, is found by branch and the lot closes. A pull request found by branch is the lot's only when its head is a commit the branch reached since the lot was created, so a branch name reused by a new lot never takes an older lot's merged pull request. `lot status` still asks only for a stack parent that was pushed.
- `worktree prune` keeps a worktree whose branch's work is not in the base and whose lot did not land with `not landed: its work is not in <base>`.
